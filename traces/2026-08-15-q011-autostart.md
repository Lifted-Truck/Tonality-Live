# q011-autostart — the extension starts the bridge itself

- **Queue item:** Q-011.
- **Why:** starting `bridge/server.py` by hand was the last manual step between
  "right-click a clip" and "it works".
- **Design decisions, each verified rather than assumed:**
  - **Detached lifecycle (criterion 4).** The SDK exposes no deactivate hook —
    `ExtensionContext` is exactly application/commands/environment/resources/ui
    (read from `index.d.mts:841-896`) — so "reap on deactivate" does not exist.
    Idempotence (spawn only when nothing answers `/health`) makes a bridge that
    outlives Live *reused*, not duplicated. Same as starting it by hand.
  - **Config in `environment.storageDirectory`** — the host-writable per-extension
    dir. Machine identity never touches a tracked file; no `.env` involvement.
    (The harness correctly denies reading `.env*` — including `.env.example` —
    which shaped this: the design needs nothing from `.env`.)
  - **Sandbox pre-test.** Reproduced the host's exact flags
    (`--permission --allow-child-process --allow-fs-read=<Extensions dirs>`) in
    a standalone node and spawned the venv python against server.py: it ran up
    to `bind()` and failed only because a bridge already held the port. So the
    child is NOT bound by the fs allowlist.
- **What the live run caught that the pre-test did not.** First in-Live attempt
  failed with "Access to this API has been restricted. Use --allow-fs-read".
  Cause: I had added an `existsSync(cfg.python)` pre-flight *in Node*, and Node
  IS bound by the allowlist even though its child is not. Removed the
  pre-flight; a bad path now surfaces through spawn's own ENOENT with a clear
  message. The error path itself worked as designed (actionable, no hang,
  original error attached) — it just fired for the wrong reason. LIBRARY L0009.
- **Verified in Live, bridge deliberately down:** Analyze produced C major
  (margin 0.27) instead of an error; exactly one `bridge/server.py` process
  afterwards, parented to the Extension Host; a second command reused it (same
  PID 73906). Boot log reads `auto-start configured`.
- **Tests:** +9 in `bridgeProcess.test.ts` (22 extension tests total) — config
  round trip, malformed config, no storage dir, `/health` semantics, criterion 2
  (no spawn when up), criterion 3 (actionable message when unconfigured),
  ENOENT via spawn, a REAL spawn (this node as the "interpreter") that comes up,
  and a spawned process that never answers failing within the bound.
- **A typing artifact, noted honestly:** driving the setup dialog via UI
  automation dropped keystrokes in the WKWebView (`pyhon3`, `Docments`,
  `Douments` on three tries). Not a bug in the dialog — a human typing would not
  hit it — but I would not save a wrong path, so I wrote the config file
  directly (identical shape) and tested the thing that matters, the auto-start.
  The dialog's rendering, pre-fill, and cancel were verified visually.
- **Alternatives rejected:** tie the child to the host and kill on exit (no
  hook exists, and it would orphan anyway); put paths in `.env` (needs a
  read the sandbox and the harness both deny; and it is machine identity);
  spawn on activate rather than on demand (would start a bridge for users who
  only ever use other extensions).
- **Verify:** `./verify fast` exit 0 (22 extension tests + py_compile).
- **Open questions:** none blocking. Config UX could pre-fill from a heuristic,
  but guessing paths is exactly what "reduce, never invent" says not to do.
